# 角色与资源权限规则（第三周计划）

本文是第三周 Day 4 实现 `RolesGuard` 和资源权限判断的业务依据，属于计划采用的接口约定。Day 1 仅准备用户字段、角色与开发账号，尚未实现登录、认证 Guard 或角色 Guard。

当前第二周接口仍使用 `X-Demo-User-Id` 模拟写操作人，读取接口没有认证与资源范围限制。当前行为见 [API 契约](API.md)及[业务规则](business-rules.md)，不能将下述权限视为已经生效。

## 一、角色定义

- `EMPLOYEE`：普通员工，可以创建工单，查看自己的工单及其操作历史，并提交自己的草稿；不能执行审批通过或驳回。
- `APPROVER`：审批人，可以查看已提交的工单及其操作历史，并对待审批工单执行通过或驳回；不能创建或提交工单，也不能审批本人创建的工单。

当前采用单角色模型，每个用户只有一个角色。资源归属与业务状态仍须独立校验，角色允许某项操作并不意味着可以操作任意工单。

## 二、角色权限矩阵

| 操作               | EMPLOYEE     | APPROVER                 |
| ------------------ | ------------ | ------------------------ |
| 登录、查看本人资料 | 允许         | 允许                     |
| 创建工单           | 允许         | 禁止                     |
| 查看工单列表       | 仅自己的     | 已提交的                 |
| 查看工单详情       | 仅自己的     | 已提交的                 |
| 提交工单           | 仅自己的草稿 | 禁止                     |
| 审批通过           | 禁止         | 仅非本人创建的待审批工单 |
| 审批驳回           | 禁止         | 仅非本人创建的待审批工单 |
| 查看操作历史       | 仅自己的工单 | 有权查看的工单           |

“已提交”指状态为 `PENDING`、`APPROVED` 或 `REJECTED`。审批人不能查看 `DRAFT` 草稿。已通过、已驳回的工单仍可查看，但不能再次审批。

列表必须按当前用户的可见范围在查询时过滤；没有可见记录时返回空数组。详情和历史采用相同的可见范围，不能通过历史接口绕过工单读取权限。登录还须验证凭据与账号激活状态，角色本身不构成登录凭据。

## 三、资源归属规则

员工能够读取、提交某张工单或查看其历史的必要条件：

```text
requests.created_by = 当前登录用户.id
```

员工可以查看自己所有状态的工单，但只有自己的 `DRAFT` 可以提交。创建工单时，服务端从已认证身份设置 `created_by`，不接受客户端自行指定创建人。当前登录用户必须来自服务端验证的身份，不能直接信任 `X-Demo-User-Id` 或请求体中的用户 ID。

审批人读取工单及其历史的条件：

```text
requests.status IN ('PENDING', 'APPROVED', 'REJECTED')
```

审批人执行通过或驳回还必须同时满足：

```text
requests.status = 'PENDING'
AND requests.created_by <> 当前登录用户.id
```

虽然当前单角色模型禁止审批人创建工单，仍必须独立保留禁止自审规则，以覆盖历史归属、角色变更及未来角色扩展。查看权限不受此禁止自审规则影响。操作历史的权限依据其所属工单判断，不能仅凭某条事件的 `actor_id` 决定可见性。

## 四、业务状态规则

```text
DRAFT → PENDING → APPROVED
                ↘ REJECTED
```

| 操作 | 起始状态 | 目标状态 | 必要权限              |
| ---- | -------- | -------- | --------------------- |
| 创建 | 无       | DRAFT    | EMPLOYEE              |
| 提交 | DRAFT    | PENDING  | EMPLOYEE 且为创建人   |
| 通过 | PENDING  | APPROVED | APPROVER 且不是创建人 |
| 驳回 | PENDING  | REJECTED | APPROVER 且不是创建人 |

`APPROVED`、`REJECTED` 为终态。不能跳过提交直接审批，不能重复提交、重复审批，也不能重新提交已驳回工单。即使角色和归属检查通过，非法状态流转仍然返回 `409`。

后续权限实现必须保留现有条件 UPDATE 的并发保护，以及状态变更和事件写入的同一事务。所有权限或状态检查失败均不得修改工单或新增事件。

## 五、禁止操作及响应约定

以下均为第三周计划行为，并非当前 Day 1 接口已经实现的响应：

| 场景                                             | 计划返回 |
| ------------------------------------------------ | -------- |
| 未登录访问受保护接口                             | 401      |
| Token 无效或过期                                 | 401      |
| 被停用账号尝试登录                               | 401      |
| EMPLOYEE 尝试审批通过或驳回                      | 403      |
| APPROVER 尝试创建或提交工单                      | 403      |
| APPROVER 尝试审批本人创建的已提交工单            | 403      |
| 员工读取、提交不属于自己的工单或读取其历史       | 404      |
| 审批人读取尚未提交的草稿或其历史                 | 404      |
| 审批人尝试审批无权查看的草稿                     | 404      |
| 工单不存在                                       | 404      |
| 已登录且通过角色及资源权限检查的用户操作非法状态 | 409      |

对无权访问的工单返回与资源不存在一致的 `404`，隐藏资源是否存在，不返回该工单的内容、状态或操作历史。

检查顺序约定为：身份认证 → 操作所需角色 → 资源可见性与归属 → 禁止自审 → 业务状态。`409` 只用于已有权访问并执行该类操作的用户，不能通过状态错误向无权用户泄露资源信息。列表通过过滤隐藏不可见记录，不因存在其他用户的工单而返回 `404`。
